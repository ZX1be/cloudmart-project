# CloudMart 下一步开发计划

> **计划基线：2026-09-29 项目现状盘点**
> **目标：** 先把秒杀从“有高并发组件”推进到“核心不变量可测试、故障可恢复、容量可解释”，再扩大业务和集群规模。下列均为建议路线，尚未实施。

## 1. 交付原则

1. **先正确、再快、后扩容。** 先明确库存与订单不变量，再做压测优化，最后做多节点部署。
2. **每条异步链路要有持久状态、幂等键和补偿终态。** 不能只依靠 Redis TTL、消息 ACK 或日志推断业务完成。
3. **所有成功指标必须可复现。** 记录硬件、配置、版本、脚本、流量模型、成功订单 TPS、端到端延迟和库存对账。
4. **代码变更逐批评审。** 对当前已纳入版本的实现补充运行测试；后续新增内容先核对意图、敏感信息、schema 依赖和构建状态，不覆盖或清理已有文件。
5. **发布门禁按风险分阶段。** P0 未通过前不做生产容量承诺；文档计划不代表代码已经完成。

## 2. 阶段总览

| 阶段 | 优先级 | 目标 | 退出条件 |
|---|---|---|---|
| 0. 版本与构建基线 | P0 | 收敛仓库/文件边界，冻结可复现版本 | 文档与源码已入 Git；部署资产边界明确；干净检出可构建；schema 迁移可重复验证 |
| 1. 秒杀正确性闭环 | P0 | 定义库存、资格、订单、消息和补偿状态机 | 并发/重放/故障测试均满足不变量并对账 |
| 2. 授权与数据安全 | P0 | 关紧网关边界、管理员权限、凭证和数据访问 | 直连/伪造头/越权/泄密测试通过 |
| 3. 自动化测试与故障恢复 | P1 | 把业务不变量纳入持续回归 | CI 可运行单测、集成测试和关键故障场景 |
| 4. 可观测性与容量基线 | P1 | 看得到积压、延迟、拒绝和库存差异 | 有仪表盘、告警、容量报告和复测脚本 |
| 5. 生产化与横向扩展 | P2 | 基于真实瓶颈配置 HA、隔离与扩容 | 多实例故障切换、容量及恢复目标验收通过 |

## 3. 阶段 0：版本、仓库与数据库基线（P0）

### 工作项

- 对已纳入本次版本的 Outbox、消费者、管理端接口和前端文件进行持续审阅；后续新增实现先检查归属、构建状态、敏感信息与 schema 依赖，再提交。
- 当前 Git 仓库内已包含版本化 README 与 `docs/`；盘点工作区父目录的文档副本，以及 Compose、SQL、部署脚本与内层 Git 根的长期关系，制定避免文档副本漂移的方案；不要在没有审阅时移动或覆盖数据。
- 定义唯一的开发基线：JDK/Maven/Node 版本、依赖锁定、启动命令、配置来源及环境变量清单；提交构建说明。
- 为数据库选择统一迁移工具/机制（如 Flyway 或 Liquibase，需先评估与现有 SQL 的兼容），为每次 schema 变化建立有序、不可变迁移。
- 对比 `init.sql`、迁移脚本、实体、Mapper 和真实业务路径涉及的表/列/唯一索引；统一空库初始化和已有库升级策略。
- 给 Compose 依赖配置健康检查/就绪验证和合理启动等待；区分本地开发配置与生产密钥配置。

### 验收标准

- 干净检出后可按文档构建后端与前端；构建结果及工具版本可复现。
- 空 MySQL 数据卷初始化后 schema 完整；已有库升级、重复执行迁移、迁移失败恢复均有测试记录。
- 每个源码文件都有明确版本归属，敏感压测数据不会意外进入代码库。
- CI 至少执行编译、前端类型检查/构建和测试；正式发布门禁不使用 `-DskipTests`。

## 4. 阶段 1：秒杀正确性闭环（P0，首要业务里程碑）

### 4.1 定义不变量与业务状态机

建议先形成设计文档和可审计状态转换，再实现：

- 对每个活动：成功订单数不超过可售库存；数据库库存、Redis 可售库存、预占库存和未决补偿之间有明确关系。
- 对每个用户/活动：最多一个有效资格/成功订单；重试同一请求不能重复扣库存或重复建单。
- 每个预占都有唯一业务键、创建时间、状态和最终结果；订单成功、业务失败、超时释放、人工处理均可追踪。
- 用户取消、支付超时、消费者重投、消息重复、补偿重试不会二次加减库存。

可考虑状态示例：`NEW → RESERVED → MESSAGE_PENDING → ORDERED`，失败路径进入 `COMPENSATING → RELEASED` 或 `MANUAL_REVIEW`。最终名称和转换必须结合现有数据模型设计，不应直接照抄。

### 4.2 收敛 Redis 资格与库存决策

- 将“用户是否已参与”与“库存是否充足、扣减/预占”的判定收敛到单次原子 Redis 脚本，或设计可证明等价的原子协议。
- 为活动时间、活动状态、每人限购数、用户资格等定义服务端权威校验；购买接口不能只依赖活动列表过滤。
- 处理 Redis 超时的“执行结果未知”场景：客户端重试应带稳定请求幂等键，通过持久化状态确认是否已经预占。
- 定义 Redis key 生命周期、活动结束后的清理、预热幂等和运行中禁止覆盖实时库存的规则。

### 4.3 持久化、消息与 Outbox

- 秒杀预占与待发消息必须有可靠关联。评估将秒杀也纳入事务 Outbox；若采用 Outbox，应保证业务状态和消息记录在同一数据库事务写入。
- 为 Outbox 消息实现原子领取/租约（多实例安全）、有限重试与退避、最大重试/死信、人工重放和审计。
- 明确 RabbitMQ 的持久化队列/消息、publisher confirm、mandatory return、消费者 ACK、DLQ 及积压处置策略。
- 消费端按稳定业务键幂等；先检查业务处理是否已提交，再决定 ACK/重试/补偿。不可在无法确认事务结果时无条件回补库存。
- 补偿任务本身也要有唯一键、并发领取、超时、重试上限、最终人工介入状态，且操作必须幂等。

### 4.4 对账与数据约束

- 为同一活动提供 Redis 与数据库/订单预占记录的对账任务；发现不一致时先告警、留痕、人工确认或安全的修复流程，避免自动覆盖造成二次错误。
- 添加数据库唯一约束：用户-活动唯一资格、订单幂等键唯一、消息业务键唯一、库存扣减业务键唯一；约束和写入冲突要映射为幂等业务结果。
- 定义库存“可售/预占/已售/已释放”的账务口径，使取消和支付超时的库存回补可追溯。

### 验收标准

- 使用大量不同用户和重复用户的并发测试；数据库对账满足成功订单数不超过初始库存，单人限购满足约束，所有库存变化可追溯。
- 对相同消息重复投递、Consumer 重启、DB 提交后 ACK 失败、Broker 不可用、Redis 超时、Outbox 多实例并发运行、补偿任务重启做故障注入；最终状态符合不变量且没有库存漂移。
- 任意预占在规定 SLA 内进入成功、释放或人工待处理终态；无无限期悬挂记录。
- 活动开始/结束边界、预热重复执行、库存不足、恶意重放、幂等键冲突均有自动化用例。

## 5. 阶段 2：安全与权限（P0）

- 建立明确的信任边界：公网只进 Gateway；Auth/Product/Order 仅内部网络可达，或每个服务自身也验证身份。移除本地 Compose 直出端口的生产照搬可能。
- Gateway 删除/覆盖客户端提交的身份上下文头，再由验证后的 JWT 生成；下游禁止信任未经验证的 `X-User-Id` / `X-Role`。
- 逐个审计管理员 API 的角色授权，包括新增管理端接口；前端菜单隐藏只能改善体验，不属于安全控制。
- 将 JWT 签名密钥、数据库与 MQ 凭证置于环境密钥/Secret 管理，配置轮换与最小权限；禁止使用开发默认凭证上线。
- 定义 CORS、TLS、密码策略、刷新令牌撤销/轮换、敏感字段脱敏、管理操作审计和登录/领取/秒杀频率限制。
- 对参数校验、水平越权、越权访问地址/订单、重放、暴力登录、限流绕过和错误响应信息做安全测试。

### 验收标准

非管理员调用所有管理 API 得到拒绝；绕过网关访问业务服务不可达或仍无法绕过认证；客户端伪造身份头不能改变下游身份；仓库和构建产物不包含生产密钥；安全测试报告无未处置的 P0/P1 问题。

## 6. 阶段 3：自动化测试与故障恢复（P1）

- 为用户、订单、优惠券、秒杀活动和库存关键规则增加单元测试与服务集成测试。
- 通过 Testcontainers 或独立测试环境验证 MySQL、Redis、RabbitMQ 行为；Mock 不可代替 Redis Lua 原子性、数据库唯一约束和 MQ ACK/DLQ 的真实集成验证。
- 将并发不变量测试纳入 CI：成功下单数、用户唯一性、扣回补账、库存对账、重复消息幂等。
- 自动化验证异常映射、交易事务边界、跨服务超时/重试、依赖重启后恢复和迁移兼容。
- 为前端补充关键流程的类型检查与端到端冒烟测试；管理界面显示异步订单最终状态，而非把接口受理当作订单成功。

### 验收标准

CI 在每次合并运行；测试数据隔离、可重复；核心状态转换及补偿路径有覆盖率/用例清单；失败能阻止合并；测试失败不会依赖手动清理开发机状态。

## 7. 阶段 4：可观测性与可信容量基线（P1）

### 指标与日志

- 使用统一 `traceId`、`requestId`、`activityId`、`orderNo`、`messageKey` 关联 Gateway、Order、Product、Publisher、Consumer 与补偿任务日志。
- 关键指标：请求成功/业务拒绝/技术失败率，成功订单 TPS，端到端下单耗时分位数，Redis 脚本耗时/错误，MQ queue depth/consumer lag/DLQ 数，Outbox 最老消息年龄与失败率，补偿任务积压，DB 连接池和慢查询，Redis 与业务账本库存差异。
- 为队列积压、消息最老年龄、死信、库存不一致、补偿超时和关键依赖不可用设置告警、runbook 与负责人。
- 提供 readiness/liveness 探针；避免“进程活着”被误认为依赖就绪或业务可接单。

### 压测方法

- 将压测端与服务端分机；记录 CPU/内存/磁盘/网络、容器限制、数据库/Redis/MQ 配置、应用版本、数据规模和缓存状态。
- 场景区分：首页/商品读取、登录鉴权、秒杀抢购、唯一用户成功下单、重复用户重试、混合流量、MQ 积压恢复。
- 使用受控用户与活动数据，明确 JMeter 校验规则和业务状态码；分别报告入口 QPS、成功下单 TPS、业务拒绝率、技术错误率、P50/P95/P99 和积压变化。
- 每轮结束做订单、预占、Redis 库存、数据库库存和补偿记录的独立对账；对“被业务拒绝但返回 HTTP 200”等情况单独分类。
- 建立基线、逐项调整容量、复测回归；不沿用当前单机报告直接制定生产 SLO。

### 验收标准

压测脚本、配置、数据准备与报告可在隔离环境重放；性能 SLO 与实际硬件绑定；达到目标负载时错误率、延迟、订单成功量和库存一致性同时达标，而非只看 QPS。

## 8. 阶段 5：生产化与横向扩展（P2）

仅在正确性和观测闭环通过后开展：

- 以压测结果定位瓶颈，再决定无状态服务副本、连接池、线程池、缓存、SQL 索引和消费者并发；避免无数据地“加机器”。
- 为 Nacos、MySQL、Redis、RabbitMQ 设计 HA/备份/持久化/恢复目标；选择满足消息与一致性要求的队列类型和副本策略，并验证故障切换。
- 使用专用服务账号、网络策略、TLS、Secret 管理、镜像扫描、资源/优雅停机配置、健康探针和滚动发布。
- 建立数据库备份、恢复演练、消息/DLQ 运维、活动库存初始化审批和紧急熔断/限流预案。
- 前端管理功能和业务扩展在服务端授权、可观测和一致性规则稳定后推进。

### 验收标准

单实例崩溃、节点/依赖故障、滚动升级和恢复演练达到预设 RTO/RPO；N+1 扩容带来可解释的容量提升；在目标负载下没有不可控队列增长、订单丢失或库存偏差。

## 9. 推荐的近期迭代顺序

1. **建立基线：** 盘点未跟踪文件、决定 Git 边界与版本归属；对齐 schema 和可复现构建。
2. **写清秒杀状态机与不变量：** 先评审设计，再实现资格/库存原子决策、持久化幂等键和可靠消息方案。
3. **验证失败路径：** 建立重复消费、Broker/Redis/DB 故障和补偿恢复集成测试。
4. **关安全边界：** 管理员授权、网关头信任、服务端口隔离、密钥管理。
5. **接入 CI 与指标：** 测试成为合并门禁；为成功订单 TPS、队列积压和库存差异建立观测。
6. **重新压测并出容量报告：** 使用独立压测端、可审计数据与库存对账，之后再讨论集群扩容和生产 SLO。

## 10. 里程碑定义

### M1：可重复构建

干净检出、配置外置、迁移脚本和构建门禁就绪；工作区父目录与仓库内副本的归属清晰。

### M2：秒杀一致性闭环

并发、重复、崩溃、重试和补偿场景均有自动化证明；库存对账无漂移；悬挂预占可恢复。

### M3：安全与运行可见

授权边界通过负向测试；日志/指标/告警覆盖订单、消息、补偿和库存一致性。

### M4：容量与生产部署评审

独立压测报告满足容量目标，依赖 HA、备份恢复、故障切换和运维手册通过演练。只有 M1–M4 均完成后，才建议将项目从演示/验证用途升级为真实促销业务候选系统。
