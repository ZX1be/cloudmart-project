# CloudMart 项目现状与风险分析

> **盘点日期：2026-09-29**
> **盘点范围：** Java 微服务、前端、Compose、SQL、部署脚本、Git 状态及盘点期间可读的压测摘要。
> **验证声明：** 已执行后端 `mvn -o -DskipTests clean package` 和前端 `npm run build`，两者均成功；后端测试被跳过。没有运行服务、部署、压测或数据库/Redis 对账，因此以下不是端到端运行验收报告。

## 1. 结论摘要

CloudMart 已具备完整的电商练习项目骨架和若干高并发设计要素：微服务拆分、Redis 缓存、秒杀库存 Lua、RabbitMQ 异步消费、订单/库存幂等相关表和消息处理代码。当前当前版本包含统一 Outbox 发布组件、补偿任务实体、库存消息消费者及管理端接口等实现；其代码接线已静态审阅，但未作运行验收。

但从企业级高并发秒杀视角，**目前不能判定为生产就绪，也不能据现有文件证明“全链路不超卖、无重复、消息不丢、故障可自动恢复”。** 主要原因：本次纳入版本的 Outbox 与业务接线尚未做运行/故障验收；秒杀的用户去重和库存扣减不是同一 Redis 原子操作；秒杀发布仍走直接发送；消费失败时直接尝试回补库存并转入死信的边界未验证；活动购买时间校验、数据库迁移、角色授权、自动化测试、故障演练和容量指标都需要完善或形成证据。

**成熟度判断：** 适合作为微服务电商与异步秒杀的学习/演示项目；尚不具备足以支撑真实促销的完整一致性、可恢复性、安全和运维验收闭环。

### 2.3 目录及运行形态

Maven 根版本为 `1.0.0`，包含 `common`、`gateway`、`auth`、`product`、`order` 五个模块；前端是独立 Vue 项目。Compose 配置单机运行 Nacos 2.1.0、MySQL 8、Redis 6.2、RabbitMQ 3.13 与四个后端服务/前端容器。应用配置指向同一 MySQL 实例及 `cloudmart` 数据库。

这是一套便于开发演示的单机组合，不是生产高可用拓扑：Compose 没有可见的健康就绪闸门；数据库、中间件及应用端口被映射到宿主机；Nacos 为单机模式；未见生产 profile、资源配额和多节点部署编排。

## 3. 业务能力盘点

### 用户与认证

代码包含注册、登录、刷新令牌、用户资料及地址接口；密码编码采用 BCrypt。Gateway JWT 过滤器解析令牌并向下游添加用户 ID、用户名和角色上下文。Auth 服务的 Spring Security 配置依赖“Gateway 层做 JWT 校验”的边界，因此必须确认服务端口不可被不可信网络绕过访问，并验证下游对透传头的信任方式。

### 商品

代码包含商品列表/详情、分类树、评价、收藏、管理端商品和分类接口；商品详情/分类存在缓存逻辑。Product 还承担普通订单商品库存扣减/恢复职责。若网关和商品服务都能被外部直接访问，需要验证鉴权边界、缓存失效和库存更新路径。

### 订单与优惠券

包含购物车、订单创建/查询/状态操作、取消订单和库存恢复、用户优惠券领取/查询等服务接口。管理优惠券、订单和秒杀的新增控制器已纳入本次版本，静态代码中包含管理员角色检查；尚未做负向授权或完整前端到 DB 端到端验证。

### 秒杀

存在活动列表/购买入口、管理员活动/预热相关接口文件、Redis 库存键、Lua 库存脚本、用户参与标记及 RabbitMQ 建单消费者。代码路径分析见下一节。仅凭模块和组件存在，不足以证明并发正确性。

## 4. 秒杀与库存链路分析

### 4.1 当前可见路径

```text
请求 → Gateway 鉴权/限流 → Order 检查活动
  → Redis setIfAbsent 用户参与标记（30 分钟 TTL）
  → Lua 原子校验并扣减秒杀库存
  → 直接发送 RabbitMQ 消息
  → SeckillOrderConsumer 异步创建订单
```

库存键为 `seckill:stock:<activityId>`，用户标记键为 `seckill:order:flag:<activityId>:<userId>`。Lua 对给定活动库存执行检查和扣减，可避免该脚本内的并发超扣；但用户标记和 Lua 是两次独立 Redis 操作，不构成跨两个键的原子决策。消费者出错时会增加 Redis 库存、删除用户标记，并以不重回队列的方式 NACK；队列配置了死信相关组件。

### 4.2 关键正确性与恢复风险

1. **活动时间校验：** 活动列表筛选开始/结束时间；购买方法中可见的判断主要是活动存在及状态，不足以证明购买入口也严格校验活动窗口。购买接口应自行校验并覆盖边界时间测试。
2. **用户资格与扣库存原子性：** Redis 参与标记与 Lua 扣库存分离。要定义失败/超时/重试时各键的状态，并确保同一用户最多一个有效预留/订单。
3. **消息发布可靠性：** 秒杀路径当前可见为直接 `convertAndSend`；没有看到该路径先落本地 Outbox 的证据。进程在 Redis 扣减后、Broker 确认前后崩溃时需要可恢复方案。
4. **补偿时机：** 消费者遇到异常就回补 Redis；如果业务事务已提交但 ACK/连接故障引发重投，简单回补可能造成 Redis 库存与已创建订单不一致。必须基于持久化业务状态进行幂等补偿，而不是只看消费是否抛异常。
5. **去重生命周期：** 用户标记 TTL 为 30 分钟。消息积压、延迟或进程故障超过该时间时，标记可能先于业务终态过期。需要持久化唯一约束与明确的预留超时/释放协议。
6. **库存源与重建：** 预热逻辑将活动表库存写入 Redis。若活动运行中再次预热，有覆盖实时 Redis 库存的风险；需要活动状态门禁、预热幂等规则、库存对账与恢复流程。
7. **状态模型：** 尚需把“已预扣、待消息、建单成功、业务失败、补偿中、已释放、死信待处理”等状态统一为可查询的业务状态机，并明确每个转换的幂等键和唯一约束。
8. **故障演练缺口：** 未见针对 Redis/MQ/MySQL 中断、Broker 确认丢失、消费者提交后宕机、重复投递、DLQ 堆积、补偿任务重启的自动化演练证据。

### 4.3 Outbox 当前状态

工作区新增了公共 Outbox 实体/Mapper/Publisher，发布任务周期性读取待发送记录、使用 Rabbit 确认并标记发送/重试；Order/Product 的库存事件路径也出现相关引用。此部分源码已通过本次 Maven `clean package` 编译并纳入版本管理；但没有 Outbox 集成/故障测试，不能据此认定运行闭环已验收或消息类型完整覆盖。

尤其需要确认：

- 秒杀消息是否也改为“业务状态/库存预留 + Outbox 同事务落库”；当前所见秒杀入口仍直接发送；
- 多实例 publisher 是否有原子领取/租约，避免竞争领取同一行；
- 重试是否指数退避、是否有最大次数/死信和人工重放；
- confirm、mandatory return、DB 提交与发布标记之间崩溃时如何保证至少一次投递；
- 消费端幂等键是否能识别“已成功但未 ACK”的重复消息；
- Outbox 堆积、最老消息年龄、发送失败率是否有指标和告警。

## 5. 数据一致性与数据库

`sql/init.sql` 中可见订单幂等记录、库存扣减/恢复记录、统一 Outbox 和补偿任务等表结构；工作区还包含一份旧 Outbox 表合并迁移脚本。它们说明项目正在向幂等/可靠消息演进，但尚未形成统一的 schema 管理与部署流程：

- MySQL 容器初始化脚本只在数据卷首次初始化时自动运行；已有库不会因 `init.sql` 改动自动升级；
- 迁移脚本是否按版本、顺序、环境执行及回滚方式尚无统一约束；
- 必须校验实体、Mapper、表名/列名、唯一索引与实际 schema 一致；
- 订单、商品、活动库存分属业务模块但目前共享 MySQL 实例，不能等同于跨服务数据库事务或生产级隔离。

迁移前应备份数据并在空库、已有库、重复执行和部分失败场景做验证。

## 6. 安全、部署与运维

- Gateway 负责 JWT 校验并透传身份头；多个后端端口在 Compose 中直接发布到宿主机。生产部署必须限制入口、隔离服务网络，并验证伪造 `X-User-Id`/`X-Role` 不能越权。
- 管理端接口的管理员角色约束需要逐个审计并用非管理员 token 做拒绝测试，不能只依据前端隐藏菜单。
- Compose 中存在开发用凭证配置；不要用于生产，也不要将密钥写入文档、日志或 Git。
- 未见本次可确认的 CI、健康检查、分布式追踪、统一指标面板、告警规则、备份恢复演练或 DLQ 运维流程。
- `deploy.ps1` 的 Maven 命令使用 `-DskipTests`；脚本默认成功不代表测试通过。
- `sql/init.sql` 自动初始化仅适用于新的 MySQL 数据卷；升级数据库须走经过审阅的 migration。
